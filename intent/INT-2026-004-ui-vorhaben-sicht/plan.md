## In einfachen Worten

**Worum geht es?** Die Web-UI von Specwright ist heute für einen Arbeitsablauf gebaut, den es seit Version 4.0.0 nicht mehr gibt: Sie zeigt Specs, Story-Karten und ein Kanban-Brett und startet je Story eine eigene Claude-Sitzung. Seit dem 14.09. läuft jede Änderung stattdessen als „Vorhaben" — ein Ordner mit drei Dokumenten (Absicht, Spec, Plan), die Claude schreibt und die Michael an vier Stellen freigibt. Diese Freigaben tippt Michael heute im Terminal, und die Dokumente liest er in MacDown oder auf GitHub. Am Handy geht beides schlecht. Die UI soll deshalb umgebaut werden: Sie zeigt die Vorhaben aller offenen Projekte, macht die Dokumente lesbar, und Michael kann direkt im Dokument Anmerkungen schreiben, sie an die wartende Claude-Sitzung schicken oder das Dokument freigeben. Dazu kommt eine Projekt-Seite, auf der er die fünf Grunddokumente eines Projekts (Product Brief, Architektur, Sicherheit, Design, CLAUDE.md) lesen und bearbeiten kann. Der alte Story-Pfad verschwindet aus der Oberfläche. Der Rahmen — Seitenleiste, Projekt-Reiter, Cloud-Terminal, Einstellungen, Team, die Handy-Leisten — bleibt, wie er ist.

**Was ändert sich für Michael?** Nach dem Öffnen der UI steht als Erstes eine Liste „Vorhaben": pro Zeile Projekt, Kennung, Titel, Phase und ein Zustand wie „wartet auf dich · Plan · plan.md". Was auf ihn wartet, steht oben. Ein Klick öffnet das Vorhaben mit seinen Dokumenten; das Dokument, um das es gerade geht, ist vorausgewählt. Beim Lesen kann er an jedem Absatz eine Anmerkung beginnen — am Mac über eine Marke am Rand, am Handy durch Tippen auf den Absatz — und die UI merkt sich automatisch, worauf sich die Anmerkung bezieht (z. B. „AK-03" oder „§6"). Unten sammelt eine Leiste die Anmerkungen; „Änderungen schicken" gibt sie gesammelt in die wartende Sitzung, „Freigeben" schickt genau eine Freigabe-Zeile. Beides funktioniert am Mac und am Handy, ohne Terminal. Ist keine Sitzung da, bietet die Seite stattdessen den nächsten Schritt an („Plan erstellen") mit Modellwahl und der Wahl, ob im Projekt oder in einem Worktree gearbeitet wird. Die Projekt-Seite liegt daneben als eigener Reiter „Projekt". Kanban, Story-Karten, Backlog und der Auto-Mode je Story gibt es danach nicht mehr — auch nicht über alte Links. Die Auslieferung geschieht in drei Pull Requests nacheinander, damit Michael früh etwas nutzen kann: erst Übersicht, Leser und Projekt-Seite; dann der Antwort-Kanal und das Starten von Schritten; zuletzt der Abbau.

**Wie wird das gemacht?** Die Grundidee: Die UI liest die Wahrheit aus Dateien, nicht aus einer eigenen Datenbank. Jedes Vorhaben ist ein Ordner mit Dokumenten, und in den Kopfzeilen dieser Dokumente steht bereits, ob sie „entwurf" oder „freigegeben" sind — der Workflow schreibt das heute schon. Das Backend der UI schaut in die Ordner aller offenen Projekte (und ihrer Git-Worktrees, weil Vorhaben oft dort entstehen), leitet daraus die Phase ab und beobachtet die Ordner mit dem Betriebssystem-Datei-Wächter, damit Änderungen innerhalb von Sekunden in der Liste stehen. Ob eine Claude-Sitzung gerade wartet, weiß das Backend bereits: Jede Sitzung meldet über kleine „Hooks" (Rückrufe von Claude Code), ob sie arbeitet, wartet oder eine Frage stellt — das treibt heute den Glocken-Ton. Aus „Sitzung wartet" plus „jüngstes Dokument ist noch nicht freigegeben" ergibt sich „wartet auf dich". Damit das Backend weiß, welche Sitzung zu welchem Vorhaben gehört, merkt es sich beim Start eines Schritts aus der UI die Zuordnung, und wenn Michael von Hand im Terminal `/plan INT-2026-004` tippt, erfährt das Backend das über denselben Hook (der die eingegebene Zeile mitliefert). Beim Senden einer Antwort tut das Backend das, was ein Mensch mit der Zwischenablage tut: Es „fügt" den Text in die Sitzung ein, so wie ein Einfügen aus der Zwischenablage aussieht (der Terminal-Standard dafür heißt „bracketed paste": der Text ist als Block markiert und wird nicht Zeile für Zeile als Eingabe gewertet), und drückt danach Enter. Sobald Claude den Text als Eingabe annimmt, meldet der Hook das zurück — daraus wird die Zeile „angenommen 16:31" im Protokoll. Anmerkungen, Protokoll und die Zuordnung Sitzung↔Vorhaben liegen in einer kleinen Laufzeitdatei auf dem Rechner des Backends, genau wie heute schon die Liste der offenen Projekte; deshalb sehen Mac und Handy dasselbe. Zum Lesen der Dokumente wird die Markdown-Bibliothek verwendet, die im Chat der UI schon Tabellen und Mermaid-Diagramme rendert; sie bekommt eine eigene Instanz, weil zwei Stellen im Code sie heute mit widersprüchlichen Einstellungen konfigurieren. Beim Bearbeiten der Projekt-Docs prüft das Backend vor dem Speichern, ob die Datei seit dem Öffnen von jemand anderem (etwa einer Claude-Sitzung) geändert wurde, und lässt Michael dann wählen: neu laden oder trotzdem überschreiben. Gespeichert wird ohne Commit.

**Was kann schiefgehen?** (1) Das Einfügen in die Sitzung ist der einzige Teil, den ich nicht am Code beweisen kann; es ist der Weg, den Michael täglich beim Einfügen aus der Zwischenablage nutzt, aber er wurde noch nie programmatisch durch tmux hindurch getestet. Deshalb ist der erste Schritt der zweiten Stufe ein Versuch mit einer echten Sitzung; klappt er nicht, gibt es einen belegten Ausweichweg über tmux selbst. (2) Ein Neustart der UI (bei jedem Merge auf `main`) könnte eine gerade gesendete Antwort verschlucken; deshalb wird die Antwort erst auf Platte geschrieben, dann gesendet, und die Neustart-Sperre bleibt bis zur Bestätigung — höchstens 10 Sekunden. (3) Nach einem Neustart weiß das Backend heute nicht mehr, ob eine Sitzung wartete; das wird behoben, indem der letzte Zustand mit in die Sitzungsliste auf Platte geschrieben wird. (4) Die dritte Stufe löscht sehr viel Code (mehr als 40 Dateien und rund 40 Testdateien); das Risiko ist, dass etwas mitgelöscht wird, das der Rahmen noch braucht. Dagegen steht eine Lesevorprüfung vor jedem Löschen und die Regel, dass jede Stufe für sich `verify: OK` liefern muss. (5) Die Handy-Bedienung (Tippen auf Absatz) kann mit dem Scrollen kollidieren; deshalb öffnet ein Tippen erst eine kleine Leiste mit „Anmerkung", nie sofort ein Eingabefeld. Rückgängig ist alles per Revert des jeweiligen Merge-Commits; Daten in den Projekten werden nicht verändert.

**Was musst du entscheiden?** Zwei Kleinigkeiten, beide mit Vorschlag: (a) Das Vorhaben INT-2026-004 selbst liegt nur in diesem Worktree; der erste Pull Request nimmt den Ordner mit — einverstanden? (b) Bis die dritte Stufe gemergt ist, heißt der alte Bereich in der Seitenleiste weiter „Dashboard" und die neuen Reiter „Vorhaben" und „Projekt" stehen darüber — oder soll „Dashboard" schon in Stufe 1 ans Ende der Liste? Vorschlag: nach oben „Vorhaben", „Projekt"; „Dashboard" bleibt bis Stufe 3 an alter Stelle. *Beides angenommen mit der Freigabe, Product Owner 2026-09-15.*

## 1. Kurzfassung

Das Backend bekommt einen **Vorhaben-Dienst** (Reader, Datei-Wächter, Zustandsdatei, WS-Handler nach dem Muster des Workspace-Stores), der aus `intent/`-Ordnern der offenen Projekte und ihrer Worktrees Phase und Zustand ableitet, Sitzungen über den bestehenden Hook-Kanal zuordnet und Antworten als Bracketed-Paste plus Enter in die wartende PTY schreibt. Das Frontend bekommt eine neue Arbeitsfläche (`aos-vorhaben-view` mit Übersicht, Vorhaben-Seite, Dokument-Leser, Anmerkungen, Sende-Leiste; `aos-projekt-seite` mit Doc-Editor), die den bestehenden Rahmen (app.ts, Mobile-Shell, Terminal-Sidebar) unverändert nutzt. Drei Stufen (B-10): Stufe 1 Übersicht + Leser + Projekt-Seite, Stufe 2 Review-Kanal + nächster Schritt + Modell-Standards, Stufe 3 Abbau des Story-Pfads samt Doc-Nachzug. Am Ende: `kanban.json` kommt unter `ui/` nicht mehr vor (EK-04), `architecture.md` §1–§3, AR-03, AR-05, §10 und `design.md` §7, `product-brief.md` §5/§8, `security.md` §7 sind nachgezogen, ADR-0002 beschreibt die neue Laufzeitdatei.

## 3. Entwurf

### Ansatz

**Backend (`ui/src/server`)** — ein Dienst, vier Bausteine, Muster Workspace:

1. `services/vorhaben-reader.ts` (rein, IO nur über injizierte `fs`): `parseIntentHead(text)` (Frontmatter-Zeilen `key: "value"  ` → `intent_id, titel, status, version, bypass, herkunft?`), `parseStatusLine(text)` (`^>\s*\*\*Status:\*\*\s*(\S+)\s*(.*)$` → `{status, note}`), `derivePhase(docs)` nach Spec-Tabelle „Phasenregeln" (erste Zeile gewinnt), `deriveReviewDoc(phase, docs)` nach „Review-Punkte", `deriveZustand(phase, hasBuildStand, session)` (sieben Werte), `scanProject(projectPath, worktreeEntries)` → `VorhabenRow[]` mit Merge je Kennung (FA-06: Kopie der zugeordneten Sitzung, sonst jüngste `mtime`). Cache `Map<absPath, {mtimeMs, parsed}>` → FA-07.
2. `services/vorhaben-watcher.ts`: je Projekt + Worktree ein `fs.watch(intentDir, {recursive:true})`, Debounce 300 ms, Events `changed(projectPath)` und `dir-added(projectPath, cwd, intentId)` (für `/intent`-Zuordnung). Fallback Polling 3 s bei Fehler.
3. `services/vorhaben-state.ts` (`VorhabenStateStore`, Datei `<runtime>/vorhaben-<port>.json`, `version:1`): `assignments{[projectPath::intentId]: {sessionId, step, model, cwd, at, ended?}}`, `drafts{[projectPath::intentId::doc]: Anmerkung[]}`, `protocol: ProtokollEintrag[]`, `lastModel{[projectPath::intentId::step]: Sel}`, `docDrafts{[projectPath::docKey]: {text, openedMtime, updatedAt}}`; Writes serialisiert + atomar (tmp+rename, 0600); Prune: Protokoll-Einträge > 30 Tage **und** Vorhaben nicht mehr in der Liste.
4. `services/vorhaben-service.ts` (Orchestrierung, hält Manager/Store/Reader/Watcher/WorkspaceStore): baut den Snapshot `VorhabenState{rows, projects, drafts, protocol, lastModel, loading}`; lauscht `session.agent-event`, `session.closed`, `session.prompt-text`; `startStep()`, `send()`, `hasPendingSend()`. `services/vorhaben-handler.ts`: WS-Fassade (Nachrichtentypen `vorhaben:*`, Validierung, Reply/Broadcast) — testbar mit Fake-Broadcast wie `workspace-handler.test.ts`.

**Zuordnung Sitzung↔Vorhaben (FA-21):** ein Detektor `detectV4Command(prompt)` (`^\s*/(?:specwright:)?(intent|spec|plan|build)(?:\s+(INT-\d{4}-\d{3}))?\b`) wird an zwei Stellen gefüttert: (a) `initialPrompt` beim serverseitigen Start, (b) `session.prompt-text` aus dem Hook. Treffer mit Kennung → `assignments` (jüngste gewinnt). `/intent` ohne Kennung → `pendingIntent{sessionId, cwd, since}`; das erste `dir-added` unter `cwd/intent/` nach `since` löst die Zuordnung aus. `session.closed` → `ended:true` (Zeile bleibt „Sitzung beendet", FA-22).

**Senden (FA-27/28/30/31/33/34):** `vorhaben:send{projectPath, intentId, doc, kind, stand}` → Prüfungen (Projekt offen, Zuordnung vorhanden, Session `active`, `agentStatus ∈ {done, idle}`, bei `freigabe` `stand === mtime` und Phase ≠ PR und Review-Dokument vorhanden; sonst Grund `keine_sitzung|arbeitet|dialog|beendet|stand_veraltet|kein_review_dokument`) → Text bauen (Server ist Quelle der Entwürfe: `Änderungen zu spec.md (Stand 2026-09-15 16:42):` + `n. ### Variante A — nicht zerlegbar, drei Stufen nacheinander, je eine Sitzung

Jede Stufe = eine Bau-Sitzung; Kontextdeckel laut `build.md` Step 3 gilt (Stufe 3 könnte ihn reißen — dann `build-stand.md` und Fortsetzung, kein zweiter Worktree).
