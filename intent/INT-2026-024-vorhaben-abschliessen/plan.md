## In einfachen Worten

<!-- leser: mensch -->

**Worum geht es?** Wenn ein Vorhaben fertig gebaut und sein Pull Request gemergt ist, muss noch ein letzter Handgriff passieren: In der Absichtsdatei (`intent.md`) muss das Statuswort von „angenommen" auf „umgesetzt" wechseln, die Versionsnummer eins hochzählen, das Änderungsdatum auf heute springen und eine Zeile ins Änderungsprotokoll kommen. Das ist immer dieselbe Arbeit. Bisher erledigt das eine Claude-Sitzung — mit dem Ergebnis, dass die Sitzung manchmal ein Wort erfindet, das die Übersicht nicht kennt („in Arbeit", „abgeschlossen", „in Umsetzung"). Dann hängt die Zeile ewig unter „Läuft". Am 21.09. waren das 18 Vorhaben. Dazu hält die Übersicht Zeilen selbst dann fest, wenn das Wort stimmt: Sie zeigt die Kopie der zugeordneten Sitzung statt des Hauptcheckouts, und eine bloß wartende Sitzung reicht, um ein fertiges Vorhaben unter „Wartet auf dich" zu stellen.

**Was ändert sich?** Auf der Seite eines Vorhabens steht neben „Nächster Schritt" ein Knopf „Abschließen" — in jeder Phase außer „Absicht" und „Umgesetzt". Ein Klick öffnet einen Bestätigungsdialog, der genau sagt, was passiert: welches Vorhaben, welche Datei, welcher Stand auf dem Hauptzweig gefunden wurde (etwa „Status angenommen, Version 1.0.0 → 1.0.1"), die Protokollzeile im Wortlaut, der Zweigname und dass ein Pull Request gegen `main` eröffnet wird. Und was nicht passiert: kein Merge, `spec.md` und `plan.md` bleiben, die Sitzung und ihre Arbeitskopie bleiben, die Board-Karte ist ein eigener Schritt. Nach der Bestätigung erledigt das Backend alles ohne Sprachmodell: Es liest die Absichtsdatei vom entfernten Hauptzweig, schreibt die drei Kopffelder und die Protokollzeile, legt einen Commit auf dem Zweig `chore/INT-…-abschluss` an, pusht ihn und eröffnet den Pull Request. Ein Toast meldet „Abschluss-PR #n eröffnet". Michael merged den PR wie heute auf GitHub.

Sofort danach steht die Zeile in der Übersicht unter „Umgesetzt" mit dem Zusatz „Abschluss-PR #n" — obwohl die Datei im Hauptcheckout noch „angenommen" sagt, denn der PR ist ja noch nicht gemergt. Dafür merkt sich das Backend eine kleine Marke „Abschluss angestoßen, PR #n". Auf der Seite steht dann statt „Abschließen" der Knopf „Abschluss zurücknehmen", falls Michael das falsche Vorhaben erwischt hat oder den PR doch nicht will; die Rücknahme löscht nur die Marke, Zweig und PR bleiben (der Dialog sagt das). Solange ein Abschluss noch läuft, ist auch die Rücknahme gesperrt. Sobald Michael den PR gemergt und seinen Hauptcheckout aktualisiert hat, trägt die Datei selbst „umgesetzt" — die Marke verfällt von allein, der Zusatz verschwindet.

Unabhängig vom Knopf lernt die Übersicht zwei Regeln, die sofort für alle offenen Projekte gelten: Erstens gewinnt die Fassung im Hauptcheckout, sobald sie „umgesetzt" trägt — auch wenn eine Arbeitskopie eine ältere Fassung oder ein falsches Wort hat; in jedem anderen Fall bleibt es bei der heutigen Regel (Kopie der Sitzung, sonst jüngste). Zweitens hält eine Sitzung, die nur wartet (fertig, ruhig, beendet), ein umgesetztes Vorhaben nicht mehr unter „Wartet auf dich"; nur eine Sitzung, die gerade arbeitet oder einen Dialog zeigt, tut das noch. Und der Bau-Workflow sagt am Ende nicht mehr „nach Merge intent.md auf umgesetzt setzen", sondern verweist auf den Knopf; für Projekte ohne Web-UI bleibt ein Satz, wie der Kopf von Hand aussieht.

**Wie wird das gemacht?** Der Kern ist ein Stück Backend-Code, das die Absichtsdatei nach festen Regeln umschreibt: Es sucht im Kopf die Zeilen `status:`, `version:` und `geaendert:`, ersetzt nur den Wert und lässt Anführungszeichen, Leerzeichen am Zeilenende und Zeilenumbrüche so, wie es sie vorfindet — Zeile für Zeile, sodass auch eine Datei mit gemischten Zeilenenden Byte für Byte erhalten bleibt. Dann sucht es die Tabelle unter „Änderungsprotokoll", liest die Spaltenüberschriften und hängt eine Zeile an, deren Zellen nach den Spaltennamen gefüllt werden (Version, Datum, Änderung, Autor, IDs, Freigabe). Das ist nötig: Ich habe alle 39 Absichten in den fünf Projekten auf diesem Mac durchgesehen (Specwright, kreis-lippe-audit, compass, rd-podcast, SBSDashboard) — es gibt vier verschiedene Tabellenformen, darunter eine mit „Datum" vor „Version". Alle haben die drei Kopffelder, keine hat Windows-Zeilenenden. Alles andere in der Datei bleibt unverändert. Dieses Stück ist eine reine Textfunktion ohne Dateizugriff und lässt sich deshalb mit vielen Beispielen testen (Version ohne Anführungszeichen, Windows- und gemischte Zeilenenden, alle vier Tabellenformen, fehlende Tabelle, falsches Statuswort).

Der zweite Teil bringt das Ergebnis ins Repo, ohne Michaels Hauptcheckout anzufassen. Hier weiche ich vom Wortlaut der Spec ab, nicht von ihrem Ziel: Die Spec spricht von einer „kurzlebigen Arbeitskopie" (einem zweiten Verzeichnis, wie es das Backend für Claude-Sitzungen anlegt). Ich baue den Commit stattdessen direkt in der Git-Datenbank, ohne Verzeichnis. Git kann das: Man liest den Dateibaum des entfernten Hauptzweigs in eine private, temporäre Indexdatei, tauscht darin die eine Datei aus, schreibt daraus einen Baum und einen Commit und hängt den Zweignamen daran. Der Vergleich: Statt das ganze Haus nachzubauen, um eine Tür auszutauschen, tauscht man die Tür im Bauplan und lässt den Plan als neue Fassung registrieren. Vorteile: Es entsteht kein Verzeichnis, das nach einem Absturz herumliegen und aufgeräumt werden müsste; der Hauptcheckout bleibt sicher unberührt, weil sein Index nie geöffnet wird; und es laufen keine Git-Hooks des Zielprojekts an. Das Letzte ist eine dauerhafte Eigenschaft, die man kennen muss: Ein Abschluss-Commit durchläuft nie die Commit-Prüfungen eines Projekts (etwa Formatierer oder Prüfungen des Commit-Texts). Für diese Commits ist das richtig — sie ändern eine Markdown-Datei nach festem Muster, und ihr Titel folgt der Commit-Konvention ohnehin —, und in Kreis Lippe oder Applai würde ein Commit-Hook ohne installierte Abhängigkeiten sonst zufällig scheitern. Es steht so in den Projekt-Docs. Das Ziel von AK-05 und FA-08 ist erfüllt, nur die Technik ist eine andere. Das ist Entscheidung D1 unten; der Plan nennt auch den Weg, falls du sie ablehnst.

Vor der ersten Änderung prüft das Backend alles, was scheitern könnte, und bricht dann ab, ohne etwas zu hinterlassen: Ist das Projekt ein Git-Repository mit einem entfernten Hauptzweig? Liegt das Vorhaben dort schon (sonst: „erst den Bau-PR mergen")? Ist der Kopf lesbar, die Version eine echte Versionsnummer, das Änderungsprotokoll da? Ist der Zweigname lokal und auf GitHub noch frei? Ist `gh` installiert und angemeldet? Ist eine Git-Identität (Name, E-Mail) gesetzt, ohne die kein Commit entstehen kann? Für `gh` gibt es einen Kniff: Ist in den UI-Einstellungen ein GitHub-Token hinterlegt (auf dem Droplet für den Push ohnehin nötig), bekommt `gh` genau dieses Token mitgegeben — dann braucht es keine eigene Anmeldung, und Mac und Droplet verhalten sich gleich.

Scheitert ein Schritt erst nach der ersten Änderung — der Push wegen fehlendem Netz, der Pull Request wegen GitHub —, baut das Backend zurück: Es löscht den Zweig lokal und, falls schon gepusht, auf GitHub. Vorher schaut es aber einmal nach, ob GitHub den Pull Request nicht doch angelegt hat (das passiert, wenn `gh` erst nach dem Anlegen abbricht, etwa bei einem Zeitüberschreitung): Findet es den PR, gilt der Abschluss als gelungen, nichts wird gelöscht. Lässt sich das nicht klären, bleibt der Zweig stehen, und die Meldung sagt „auf GitHub prüfen". Bleibt beim Rückbau etwas stehen, sagt die Meldung genau das („Zweig … ist auf GitHub stehen geblieben — von Hand löschen"). Eine Marke wird nur gesetzt, wenn der PR mit Nummer steht. Der Fehlgrund bleibt im Backend, bis der nächste Versuch beginnt, damit er auch nach Neuladen noch unter dem Knopf steht.

Damit zwischen Dialog und Bestätigung nichts wegrutscht, merkt sich der Dialog die genaue Fassung des Hauptzweigs (seinen Commit), die er gezeigt hat. Beim Bestätigen holt das Backend den Hauptzweig erneut und vergleicht: Hat er sich seit der Vorschau bewegt, bricht es ab und bittet, den Dialog neu zu öffnen — so wird nie etwas geschrieben, das Michael nicht gesehen hat. Das Holen geschieht mit einer ausdrücklichen Zielangabe, damit Git die Kopie des Hauptzweigs garantiert aktualisiert und nicht stillschweigend einen alten Stand liest.

Die Übersichtsregeln sind kleine Änderungen an zwei bestehenden Funktionen: Die Zusammenführung der Kopien (`ui/src/server/services/vorhaben-reader.ts:489`) bekommt als erste Regel „Hauptcheckout mit umgesetzt gewinnt" — sie greift nur, wenn der Hauptcheckout selbst „umgesetzt" trägt; für alle anderen Vorhaben ändert sich nichts. Die Gruppierung der Übersicht (`ui/frontend/src/components/vorhaben/vorhaben-sort.ts:39`) bekommt eine Zeile davor: Umgesetzte Zeilen, deren Sitzung weder arbeitet noch einen Dialog zeigt, gehen nach „Umgesetzt"; alles andere läuft wie heute. Die Marke selbst liegt im Nutzerzustand des Backends neben der Sitzungszuordnung (dieselbe Datei, dieselbe Regel: nie im Browser), sie wird mit jedem Zustandsstoß an alle Geräte geschickt und verfällt beim nächsten Lesen, sobald die Datei im Hauptcheckout „umgesetzt" trägt.

Zur Zeit: Das Backend hat für den ganzen Abschluss ein Budget von 60 Sekunden, das sich auf die Netzschritte verteilt (Hauptzweig holen, Zweig prüfen, `gh` prüfen, Push, PR — im Fehlerfall dazu Nachsehen und Rückbau). Der Browser wartet 75 Sekunden, damit eine langsame Verbindung nicht früher aufgibt als das Backend. Kommt trotzdem keine Antwort, sagt die Seite das neutral — und der wahre Stand (Marke oder Fehlgrund) kommt wenige Sekunden später über die Zeile aus dem Backend.

**Was kann schiefgehen?** Sechs Dinge, alle mit Rückweg:

Erstens: Die Textfunktion trifft eine Absichtsdatei, deren Aufbau sie nicht kennt — etwa eine Tabelle ohne die erwartete Trennzeile. Dann bricht sie mit dem Feldnamen ab, bevor etwas geschrieben wird; Michael ergänzt die Datei von Hand und drückt erneut. Kaputtschreiben kann sie nichts, weil sie nur innerhalb ganzer Zeilen ersetzt und die Tests alle vier Tabellenformen aus dem Bestand abdecken.

Zweitens: `gh` ist auf dem Droplet nicht installiert. Dann verweigert die Vorprüfung mit „gh ist nicht installiert" — nichts passiert. Ob es dort liegt, ist offen (Absicht AN-01) und wird als manueller Schritt vor der Stichprobe geprüft.

Drittens: Der Push gelingt, `gh` scheitert, und weder das Nachsehen noch das Löschen des Zweigs auf GitHub gelingt (Netz weg). Dann steht ein Zweig ohne PR auf GitHub. Die Meldung nennt ihn beim Namen; der nächste Versuch verweigert, bis der Zweig gelöscht ist. Nichts ist halb geschrieben, nur ein Zweig zu viel.

Viertens: Die neue Regel „Hauptcheckout mit umgesetzt gewinnt" verschiebt sofort Zeilen in allen offenen Projekten — gewollt, aber sichtbar: rd-podcast INT-2026-001 und kreis-lippe-audit INT-2026-012 wandern nach „Umgesetzt". Wer eine Zeile vermisst, findet sie dort. Rückweg: die zwei Regelzeilen entfernen, Verhalten ist das von heute.

Fünftens: Das Backend stürzt mitten im Abschluss ab. Es liegt dann höchstens ein lokaler Zweig ohne PR herum; die Marke wurde nicht gesetzt. Der nächste Versuch nennt den belegten Zweig und den Befehl, der ihn räumt. Kein Verzeichnis, kein Rückstand im Nutzerzustand. Eine gespeicherte „läuft"-Marke würde daran nichts verbessern — auch sie müsste beim Start gegen Git abgeglichen werden, und genau das tut die Vorprüfung.

Sechstens: Ein Abschluss-Commit läuft an den Git-Hooks des Projekts vorbei (siehe oben). Ein Projekt, das etwa eine Unterschrift im Commit-Text verlangt, bekäme sie hier nicht. Für die vier Projekte auf diesem Mac gilt das nicht; es steht als Eigenschaft in `docs/architecture.md`.

**Was musst du entscheiden?** Eine Sache, mit Vorschlag:

D1, Commit ohne Arbeitskopie: Der Abschluss baut den Commit direkt in der Git-Datenbank (temporärer Index, kein Verzeichnis) statt in einer kurzlebigen Arbeitskopie, wie Spec FA-08 und §5 sie wörtlich nennen. Ziel und Prüfung bleiben dieselben (Hauptcheckout unberührt, nichts Halbes, AK-05 mit Test). Vorschlag: annehmen. Dann werden in der Bausitzung zwei Spec-Zeilen umformuliert (§5 „Kurzlebige Arbeitskopie" → „temporärer Index", §7 Aufräumer-Zeile → „entfällt") mit einem Vermerk in der Spec-Checkliste „D1, Plan-Freigabe vom (Datum)"; kein neuer Freigabelauf, kein ADR (eine Technikwahl, keine Datenhaltung). Lehnst du ab, gilt der Rückfallweg in den Details (§3 „Rückfallweg ohne D1"): kurzlebige Arbeitskopie `…-worktrees/abschluss-INT-…`, Aufräumen beim Backend-Start, Hooks des Projekts abgeschaltet, etwa zwei Stunden mehr. Ok?

Sonst nichts — Freigabe reicht. Die Stichproben (AK-04, AK-10) laufen an echten Vorhaben, die ohnehin abzuschließen sind: INT-2026-021 in diesem Repo (trägt „in Arbeit", PR #85 gemergt — Ablauf F) am Mac; kreis-lippe-audit INT-2026-009/-010/-011 („in Umsetzung") auf dem Droplet.

### 1. Kurzfassung

<!-- leser: mensch -->

Zwei neue Server-Module tragen den Abschluss: eine reine Textfunktion (`vorhaben-abschluss-text.ts`: Kopffelder zeilenweise ersetzen, Protokollzeile nach Spaltennamen anhängen, Bau-PR-Nummern aus der Plan-Statuszeile) und ein Git-Runner (`vorhaben-abschluss.ts`: Vorschau und Abschluss über `git fetch` mit explizitem Refspec → Plumbing-Commit im temporären Index → `git push` → `gh pr create`, mit Vorprüfung, PR-Nachprüfung und Rückbau; `exec` injizierbar). `VorhabenService` orchestriert unter `withMainProjectLock`, hält „läuft" im Speicher und Marke/Fehlgrund im `VorhabenStateStore` (neue optionale Map `abschluesse`, ADR-0002-Erweiterung, im ADR als solche vermerkt). Drei neue WebSocket-Nachrichten (`vorhaben:abschluss.vorschau`, `.starten`, `.zuruecknehmen`) laufen über den bestehenden Handler mit derselben Validierung wie `session.assign`. Die Zeile bekommt `abschluss` (Marke, läuft, Fehler); der Reader hebt bei Marke die Phase auf `umgesetzt` und setzt `phaseNote` „Abschluss-PR #n"; `mergeCandidates` bevorzugt einen `umgesetzt`-Hauptcheckout (FA-13, nur dann); `groupOf` lässt nur arbeitende oder dialogische Sitzungen eine umgesetzte Zeile festhalten (FA-14). Die Vorhaben-Seite bekommt Knopf, Dialog, Hinweis-Zeile und „Abschluss zurücknehmen". `build.md` Schritt 6 verweist auf den Knopf; vier Projekt-Docs und ADR-0002 werden nachgezogen (AR-03-Text, §3 Nutzerzustand, §5 GitHub, Hook-Eigenschaft).

#### Verworfene Alternativen

<!-- leser: agent -->

| Alternative | Warum nicht |
|---|---|
| Kurzlebige Arbeitskopie (`git worktree add … origin/main`, Datei schreiben, `git commit`) wie Spec FA-08 wörtlich | Hinterlässt bei Absturz ein Verzeichnis, das ein eigener Sweep beim Start finden müsste; `git commit` löst Git-Hooks des Zielprojekts aus (husky/lint-staged ohne `node_modules` → Fehlschlag, nicht deterministisch) — abschaltbar nur mit `core.hooksPath`-Trick; kopiert nichts Nützliches; drei Lock-Stellen statt einer. Der Plumbing-Weg erfüllt AK-05/FA-08 (Hauptcheckout unberührt: eigener Index, kein Checkout) mit weniger Teilen — D1; bleibt als Rückfallweg beschrieben |
| Datei im Hauptcheckout ändern, committen, zurücksetzen | verletzt AK-05/RB-02 (Michaels Checkout kann ungestaged sein; Zweigwechsel unmöglich) |
| PR über die GitHub-API (PAT, `fetch`) statt `gh` | zweiter Weg neben dem bestehenden `gh`-Pfad, eigener Fehlerraum, Repo-Owner/-Name aus der Remote-URL parsen; AN-S03/FA-20 nennen `gh`. `GH_TOKEN` aus dem PAT gibt denselben Nutzen (kein `gh auth login` auf dem Droplet) ohne zweiten Weg |
| Marke als eigenes Top-Level-Feld im Snapshot (`state.abschluesse`) statt auf der Zeile | Seite und Sortierung bräuchten einen zweiten Lookup je Zeile; die Phase muss ohnehin im Reader gehoben werden, also gehört die Marke dorthin, wo `toRow` sie sieht |
| Marke automatisch verfallen lassen, sobald `gh pr view` „merged" meldet | NZ-02 (kein GitHub-Abgleich); die Datei ist die Wahrheit (FA-12). Die einmalige `gh pr list`-Nachfrage im **Fehlerfall** von `gh pr create` ist kein Abgleich, sondern Teil des Rückbaus (Review E5) |
| Persistente „läuft"-Marke im Store gegen Absturz (Review E6) | müsste beim Start gegen Git abgeglichen werden (Zweig da? PR da?) — genau das leistet die Vorprüfung beim nächsten Klick; die Marke brächte nur eine zweite Wahrheit, die veralten kann; Meldung nennt jetzt den Räum-Befehl |
| Vorprüfung nur im Dialog (Vorschau) und beim Bestätigen blind schreiben | Sekunden zwischen Vorschau und Klick; `baseSha`-Vergleich plus erneute Vorprüfung kosten einen `fetch` (~1 s) und garantieren, dass geschrieben wird, was gezeigt wurde (FA-02) |
| Zweig wiederverwenden, wenn er schon existiert | AN-S02: Abbruch mit nächstem Schritt; ein alter Zweig könnte fremde Commits tragen |
| `FETCH_HEAD` statt explizitem Refspec lesen | `FETCH_HEAD` ist geteilter Repo-Zustand, den ein paralleler `fetch` einer Sitzung überschreiben kann; der explizite Refspec aktualisiert genau den Ref, den Vorschau und Schreiben lesen |
